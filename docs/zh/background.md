# 协议背景与介绍

NNRP 的全名是 `Neural Network Runtime Protocol`。

它不是为了某个单一 SDK 或某个单一模型格式临时拼出来的私有接口，而是一个面向实时 AI runtime 协作的应用层协议：它试图把“宿主如何提交任务、运行时如何返回结果、双方如何表达流控/状态/缓存/语义解释”这套公共问题，从某个具体产品里抽出来，变成稳定可复用的协议面。

## 为什么会有 NNRP

NNRP 的起点来自一个很明确的工程目标：让轻量、低性能算力设备，也能参与高质量画面生成与实时增强。

协议最初由一位擅长云、AI 模型和后端开发的工程师，与两位擅长游戏开发和图像渲染的工程师共同设计打造。最早的愿景是：

1. 把高质量神经渲染能力从本地硬件压力里解耦出来。
2. 让 AR、实时沉浸式交互和更远期的虚拟世界体验拥有统一的实时协作协议基础。
3. 避免每个宿主、每种引擎、每条传输路径都重新发明一套“提交 + 回包 + 流控 + 语义解释”的私有接口。

随着协议设计推进，我们又看到了更广的适用面：它不仅可以服务神经渲染，还可以扩展到模型实时请求、流式结果、多模态 runtime 编排，以及需要显式 session / operation / backpressure 语义的实时 AI 场景。

## NNRP 想解决什么问题

从全局看，NNRP 主要解决五类问题：

1. 如何让宿主用统一方式提交实时任务，而不是被某个 runtime 私有 RPC 绑死。
2. 如何让结果不必退化成同步 request-response，而能自然表达增量结果、部分结果、丢弃、回退、复用与终止状态。
3. 如何把 payload 的语义解释从公共层剥离出去，通过 profile 和 schema 承载，而不是把某个具体业务字段永久焊死进公共头。
4. 如何在实时链路中显式表达流控、背压和 credit，而不是把拥塞和节流藏在 SDK 私有重试逻辑里。
5. 如何让 Python、C#、Rust 等不同语言实现共享同一套协议语义，而不是各写各的“差不多实现”。

## 它不是什么

NNRP 不是：

1. 一个只为了神经渲染硬编码字段的专用协议。
2. 一个只适合离线批处理或单次同步推理的接口层。
3. 一个替代 HTTP、WebSocket、WebRTC 的传输协议本身。

更准确地说，NNRP 是一个传输无关的应用层协议面。它关注的是消息形状、语义边界、状态机与解释规则；它可以绑定到不同的可靠字节流承载上。
